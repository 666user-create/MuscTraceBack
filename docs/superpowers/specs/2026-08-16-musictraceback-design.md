# MusicTraceBack 产品设计文档

- 日期:2026-08-16
- 状态:已确认(方案评审通过)
- 技术基线:Java 17 / Spring Boot 4.1 / Maven(项目已初始化,尚无业务代码)

---

## 1. 产品概述

**定位一句话**:给音乐歌单做"身份追溯"的本地 Web 工具——用户粘贴歌单链接,系统识别每首歌的真实身份,跨平台(网易云 / QQ 音乐 / 酷狗)找出所有版本并按热度展示 Top 3;当歌曲在歌单所在平台下架或被替换成奇怪版本时,帮用户查清楚"它原来是什么、现在还能在哪里听"。

**产品形态**:本地 Web 服务,用户自行部署、自行检查。项目方只分发代码,不架设中心服务。

## 2. 背景与痛点

1. **歌灰了,连名字都丢了**:版权到期后,歌单里的歌变成灰色"因版权无法播放",有的平台连歌名歌手都不显示。
2. **歌还在,但变成了奇怪版本**:平台为保留歌单结构,自动把原曲替换为同名翻唱 / Live / Remix / 同名不同歌手的山寨版本。
3. **平台割裂**:同一首歌在网易云下架、在 QQ 可听、在酷狗只有 Live 版,用户缺乏跨平台视角。

**核心洞察**:歌单数据属于用户,但平台锁定了它。MusicTraceBack 把"歌单条目"与"歌曲真实身份"解耦,把知情权和控制权还给用户。

## 3. 目标用户

| 用户群 | 特征 | 核心诉求 |
|---|---|---|
| 歌单大户(核心) | 收藏 500+ 首,重度依赖单一平台 | 下架时知道歌去哪了,快速找到替代平台 |
| 多平台用户 | 同时使用 2-3 个平台 | 跨平台对比同一首歌的版本与热度 |
| 版权敏感型用户 | 常遇歌单"缩水" | 定期体检歌单,及时发现被替换的版本 |

## 4. 核心概念

- **真实身份(Canonical Track)**:一首歌的本质标识,由"规范化歌名 + 规范化歌手"唯一确定(可选加强:ISRC / MusicBrainz MBID)。歌单条目和各平台版本都映射到这个身份。
- **版本(Version)**:同一真实身份下的不同录音——原版、重录、Live、翻唱、Remix、Demo、伴奏等。
- **曲目状态**:对每个歌单条目标记 `正常 / 已下架 / 被替换 / 仅他平台可听`。
- **快照(Snapshot)**:每次注入歌单时保存一份曲目状态快照,形成历史,用于追溯"原来是什么"。
- **置信度(Confidence)**:身份/版本判断的确定程度,分 `高 / 中 / 低` 三级。

## 5. 平台范围(已确认)

- **第一优先级**:网易云音乐、QQ 音乐、酷狗音乐(国内最主流三款)。
- 每个平台能力:解析歌单分享链接、搜索歌曲、获取歌曲详情(歌手/专辑/时长)、获取热度数据。
- 平台间地位对等,不做"主平台"概念——任意平台歌单都可注入,查询覆盖全部三平台。

## 6. 功能需求(FR)

### FR-1 歌单注入
- 用户粘贴网易云 / QQ / 酷狗的歌单分享链接或 ID → 解析出曲目列表(歌名、歌手、平台内歌曲 ID、封面)。
- 支持一次性注入多个平台歌单(各自独立成快照)。

### FR-2 曲目身份解析
- 对每个歌单条目做规范化(去掉 feat./括号修饰、繁转简、全角转半角、统一大小写、去多余空格),再通过平台搜索匹配出真实身份。
- 输出置信度分级:`高(自动确认)` / `中(疑似,需用户确认)` / `低(无法解析,人工兜底)`。

### FR-3 跨平台版本发现
- 以真实身份为输入,在三平台搜索所有候选版本并聚合为版本列表。
- 识别每个候选版本的**版本类型**(原版 / Live / 翻唱 / Remix / 伴奏 / 其他)。

### FR-4 Top 3 流行版本展示
- 对每首歌展示热度最高的 **3 个版本**:平台、版本类型、热度值(原始值 + 平台内相对百分位)、可播放状态、直达链接。
- 排序可切换:按热度 / 按平台。

### FR-5 下架与替换追查(产品亮点)
- **已下架条目**:展示它原来是什么(快照历史),给出其他平台的可用版本直达链接。
- **被替换条目**:识别真实曲目,提示"你收藏的其实是 X,当前列表里的是 Y(翻唱版)",并提供 X 的替代来源。

### FR-6 歌单体检报告
- 一键生成当前歌单健康报告:正常 / 已下架 / 被替换数量统计,建议迁移平台清单。

### FR-7 用户确认沉淀
- 用户可对 `中 / 低` 置信度条目确认原版或选择正确版本。
- 确认结果持久化,二次体检同一歌单直接命中缓存,并提升后续判断准确率(规则加权参考用户历史确认)。

## 7. 非功能需求(NFR)

- **NFR-1 数据源稳定性**:平台逆向接口随时可能失效,必须通过"适配层"隔离;任一平台异常不影响其他平台与整体功能。
- **NFR-2 合规底线**:只展示元数据与跳转链接;不提供音频播放/下载,不破解 DRM,不绕过登录鉴权抓取付费内容。
- **NFR-3 性能**:单歌单数百首歌曲,需并发抓取 + 限流 + 结果缓存;二次体检同一歌单应明显加快(命中缓存)。
- **NFR-4 可扩展性**:新增平台 = 新增一个 Adapter 实现,不改核心逻辑。
- **NFR-5 部署简易**:单机可跑,零外部依赖(内嵌数据库),一键脚本启动。

## 8. 架构设计

### 8.1 分层架构(适配层聚合,方案 A)

```
┌─────────────────────────────────────────────────┐
│  Web 层(Thymeleaf 服务端渲染页面 + REST 接口)      │
├─────────────────────────────────────────────────┤
│  应用层(用例服务)                                 │
│    PlaylistInjectionService   歌单注入            │
│    IdentityResolutionService  身份解析             │
│    VersionDiscoveryService    版本发现与聚合        │
│    HealthReportService        体检报告             │
│    UserConfirmationService    用户确认沉淀          │
├─────────────────────────────────────────────────┤
│  领域层(纯 Java,不依赖平台与框架)                  │
│    CanonicalTrack / Version / PlaylistEntry /    │
│    Snapshot / Confidence 模型 + 打分规则引擎       │
├─────────────────────────────────────────────────┤
│  适配层(Platform Adapter)                         │
│    PlatformAdapter 接口                          │
│    ├─ NetEaseAdapter       网易云                 │
│    ├─ QQMusicAdapter       QQ 音乐                │
│    └─ KugouAdapter         酷狗                   │
├─────────────────────────────────────────────────┤
│  基础设施层                                      │
│    H2 内嵌数据库(file 模式持久化)                  │
│    HTTP 客户端(RestClient/WebClient)+ 限流器      │
│    缓存(进程内 Caffeine 或简单 Map)               │
└─────────────────────────────────────────────────┘
```

### 8.2 关键接口定义

```java
// 适配层统一接口——新增平台只需实现它
public interface PlatformAdapter {
    String platformId();                              // "netease" / "qq" / "kugou"
    Playlist parsePlaylist(String shareUrlOrId);      // FR-1 解析歌单
    List<TrackCandidate> search(String title, String artist); // FR-2/3 搜索候选
    TrackDetail detail(String trackId);               // 歌曲详情(时长/专辑/热度)
    String playUrl(String trackId);                   // 跳转链接(非音频直链)
}

// 打分规则引擎输入/输出
public interface VersionScorer {
    VersionJudgement score(TrackCandidate candidate, CanonicalTrack target);
}
```

### 8.3 数据流(核心流程:注入 → 解析 → 发现 → 展示)

1. 用户粘贴歌单链接 → `parsePlaylist` 得到原始条目列表 → 落库为待解析条目。
2. `IdentityResolutionService` 对每个条目:规范化 → 平台搜索 → 打分 → 得到真实身份 + 置信度。
3. `VersionDiscoveryService` 用真实身份在三平台搜索 → 候选版本列表 → 逐条打分判类型 → 按热度取 Top 3。
4. 结果持久化进快照;页面展示 Top 3、状态标记、置信度标记。
5. 用户对 `中/低` 置信度条目确认 → 写入确认表 → 下次命中。

### 8.4 错误处理

- **平台接口失败**:捕获异常 → 该平台数据标记为"暂不可用",其余平台照常;页面明示失败原因,不整体报错。
- **解析失败(无候选)**:条目标记 `低置信/无法解析`,进入人工兜底列表,不静默丢弃。
- **超时与限流**:适配层统一配置超时(如 5s)与 QPS 限制(如每平台 2 req/s),防止触发风控。
- **应用崩溃恢复**:任务进度落库(条目级状态),重启后可续跑;H2 数据文件保证快照不丢。

### 8.5 测试策略

- **单元测试**:打分规则引擎(纯函数,覆盖各证据组合)、字符串规范化、状态判定逻辑。
- **适配层测试**:用 MockWebServer 模拟平台 HTTP 响应,不依赖真实网络。
- **集成测试**:本地起真实接口(若可用)验证三平台解析;至少保证网易云端到端跑通。
- **人工验收**:用真实歌单(含下架/替换场景)做验收清单。

## 9. 版本识别兜底策略(已确认:四层)

> 设计原则:不追求 100% 判对,而是保证"每次都知道自己有多确定,并把不确定的交给用户"。

### 第 1 层:身份解析(条目 → 标准身份)
字符串规范化(去 feat./括号修饰、繁转简、全角转半角、统一大小写、去空格)→ 平台搜索 → 匹配真实身份。纯字符串处理 + HTTP 调用。

### 第 2 层:版本识别(证据打分,规则引擎)
每个候选版本收集证据加权求和:

| 证据 | 判断方式 | 分值 |
|---|---|---|
| 歌手一致 | 候选歌手 == 目标歌手,无 feat. 他人 | 强正分 |
| 标题关键词 | 含 Live/现场/翻唱/cover/remix/伴奏/纯音乐 等 | 强负分 |
| 专辑类型 | 录音室专辑 > 精选 > 现场专辑 | 正/负 |
| 发行时间 | 最早的录音室版更可能是原版 | 弱正分 |
| 时长接近 | 与主流版本时长差 < 10 秒 | 弱正分 |
| 热度佐证 | 歌手中热度最高者更可能是原版 | 弱正分 |

分数映射:`≥80 高置信 / 40–79 中置信 / <40 低置信`。全部为 if-else + 加权求和,无机器学习。

### 第 3 层:置信度分级(透明化)
- 🟢 高置信 → 自动认定,直接进 Top 3。
- 🟡 中置信 → 展示判断依据,需用户确认。
- 🔴 低置信 → 列出候选版本,用户自选。

### 第 4 层:用户确认(最终兜底 + 数据沉淀)
- 用户确认/纠正 → 存本地库 → 二次体检命中缓存 → 规则加权参考历史确认(越用越准)。

**对入门开发者的实现建议**:MVP 先用最笨规则——"完全一致的才认、有翻唱关键词就排除、其余交给用户"。调参(关键词清单、时长阈值、权重)靠真实歌单反复测试,工作量在调参而非技术难度。

## 10. 数据模型(核心表)

```sql
-- 歌单快照:一次注入产生一个快照
SNAPSHOT(id, platform, source_url, title, created_at, status)

-- 快照条目:歌单里的每一首歌
PLAYLIST_ENTRY(id, snapshot_id, platform_track_id, raw_title, raw_artist,
               canonical_track_id,          -- 关联真实身份(null=未解析)
               entry_status,                -- NORMAL/DELISTED/REPLACED/OTHER_PLATFORM
               confidence,                  -- HIGH/MEDIUM/LOW
               judged_version_type,         -- ORIGINAL/LIVE/COVER/REMIX/INSTRUMENTAL/OTHER
               raw_metadata_json)

-- 真实身份:规范化后的唯一标识
CANONICAL_TRACK(id, normalized_title, normalized_artist, isrc, mbid,
                created_at)

-- 平台版本:同一身份在各平台的候选版本
PLATFORM_VERSION(id, canonical_track_id, platform, platform_track_id,
                 title, artist, album, duration_sec, version_type,
                 popularity_raw, popularity_percentile, play_url,
                 score, confidence, fetched_at)

-- 用户确认:沉淀用户的判断
USER_CONFIRMATION(id, playlist_entry_id, canonical_track_id,
                  chosen_platform_track_id, chosen_version_type,
                  confirmed_at)
```

缓存策略:身份解析结果与版本列表按 `(规范化歌名, 规范化歌手)` 缓存,缓存带过期时间(如 7 天),二次体检同歌单直接命中。

## 11. 页面流程(MVP)

```
首页(输入歌单链接) → 注入解析页(进度条,按条目状态推进)
  → 歌单总览页(健康报告:正常/下架/被替换统计)
    → 单曲详情页(Top 3 版本卡片:平台/类型/热度/链接 + 置信度标记
                  + 确认/纠正操作)
```

- 每首歌一张卡片:原始条目信息、真实身份、状态标记、Top 3 版本(可切换排序)。
- `中/低` 置信度卡片有醒目提示与"选择正确版本"入口。
- 体检报告页:统计图表(简单计数即可)+ 建议迁移平台。

## 12. 部署形态(本地 Web 服务,已确认)

| 档位 | 方式 | 目标用户 |
|---|---|---|
| A. 一键脚本(主打) | `start.bat` / `start.sh`,自动检测 Java 并 `java -jar` 启动,浏览器打开 `http://localhost:8080` | 绝大多数用户 |
| B. Docker 单容器 | `docker run -p 8080:8080 -v musictraceback-data:/data` | 熟悉 Docker 的用户 |

- 数据库:**H2 内嵌(file 模式)**,数据文件存于工作目录,零外部依赖,一个 jar 即整个应用。
- 无账号体系(单用户)、无 HTTPS/公网域名需求。
- 更新分发:GitHub Releases + Docker Hub 自动构建。

**架构上的连锁简化**:无需登录鉴权模块、无需 Redis/MySQL 等外部中间件、无需多节点部署。

## 13. MVP 范围(第一版只做核心闭环)

**做**:
1. 网易云 / QQ / 酷狗 三平台歌单注入(链接或 ID)。
2. 身份解析(规则版)+ 三平台版本发现。
3. Top 3 版本展示(版本类型 + 热度 + 链接)。
4. 下架 / 替换检测与追查("原来是什么 + 去哪听")。
5. 用户确认沉淀(第 4 层兜底)。
6. 最简 Web UI(Thymeleaf):输入链接 → 进度 → 结果列表 → 确认。

**不做**(YAGNI):
- 音频播放/下载、账号体系、多用户、复杂图表报表、移动端、机器学习。

## 14. 风险与合规清单

| 风险 | 等级 | 对策 |
|---|---|---|
| 平台逆向接口失效 | 🟠 高 | 适配层隔离 + 失败降级 + 定时健康检查 + 缓存 |
| 身份/版本识别准确率 | 🟠 中高 | 置信度分级 + 用户确认兜底(已内建于产品) |
| 平台 ToS / 反爬 | 🟡 中 | 本地部署分散请求 + 低频限流 + 只读元数据 + 不登录抓取 |
| 版权风险 | 🟢 低 | 仅元数据 + 外链,不提供音频 |
| 法律风险 | 🟢 低 | "发现服务 / 元数据聚合"定位 |

## 15. 技术选型(贴合入门开发者)

| 层 | 选型 | 理由 |
|---|---|---|
| 语言/框架 | Java 17 + Spring Boot 4.1(现有) | 已初始化,生态成熟 |
| 构建 | Maven(现有) | 已配置 |
| Web 页面 | Thymeleaf 服务端渲染 | 免学前端框架,适合单人开发 |
| HTTP 客户端 | Spring RestClient(或 WebClient) | 框架内置 |
| 数据库 | H2(file 模式) | 内嵌、零部署、支持 SQL |
| 缓存 | Caffeine 或简单 Map | 进程内即可 |
| 限流 | 简单令牌桶/信号量 | 避免过度设计 |
| 测试 | JUnit 5 + MockWebServer | 适配层可离线测试 |

## 16. 里程碑建议

1. **M1 骨架**:分层结构 + PlatformAdapter 接口 + H2 建表(约 1 周)。
2. **M2 单平台闭环**:网易云注入 → 身份解析 → 版本发现 → Top 3 展示(核心价值验证,约 2-3 周)。
3. **M3 三平台 + 兜底**:QQ/酷狗 Adapter + 置信度分级 + 用户确认沉淀(约 2-3 周)。
4. **M4 打磨**:体检报告、缓存、一键启动脚本、部署文档、测试补全(约 1-2 周)。

总计约 6-9 周(单人、业余时间估算,可自行压缩/调整)。
